# ADR-0013：1.0 起数据只做前向迁移，协议不兼容旧客户端

- 状态：已接受（从 1.0 起生效；在那之前 v1 基线仍可直接修改）
- 日期：2026-10-09

## 背景

1.0 之前，协议和表结构可以随时推翻：服务端的 DO 数据直接重置，本地库在版本不一致时清空，再由同步补回来。秘密聊天上线后，这条路走不通了。秘密聊天的明文与 MLS 状态只存在设备的本地库里，库一旦清空，这台设备上的历史就永久丢失，只能作为新设备被重新拉进来（见 [ADR-0010](./0010-secret-chats-multi-device-mls.md)）。同一个 OPFS 本地库由多个标签页共用（见 [ADR-0004](./0004-local-first-client.md)），新版发布后，新旧代码的标签页会同时开着。

## 决策

- **D1 与 DO 只做前向迁移，永不重置**。D1 沿用 `wrangler d1 migrations`。`UserDO` 与 `ChatDO` 各自记一个表结构版本号和一个有序的迁移数组，唤醒时只执行比版本号新的步骤；版本号一致时直接跳过，不再每次都执行建表语句。v1 就是 1.0 发布时的表结构。
- **本地库只做增量迁移**。只有库被清空（没有表，或者版本号为 0）时才重建。版本号比代码新，说明已有更新的标签页迁移过，这时不碰本地库，只重载页面。
- **协议不向后兼容，旧客户端强制重载**。`shared` 里的协议版本号随 `/ws` 一起发给服务端，不一致时服务端用专门的关闭码拒绝。标签页与同步 Worker 握手时交换构建版本，较旧的一方重载；只有新版的 Worker 当上 Leader 之后才迁移本地库。懒加载的代码块加载失败（发布后旧文件已经不存在）同样会重载。重载在通话、录音或上传进行中时推迟到结束之后，推迟期间不重连。

## 后果

- 从 1.0 起，每次改表都要写迁移步骤，不能再直接改建表语句。
- 发布新版会断开所有旧客户端，它们重载后才能重新连上；正在通话的设备要等通话结束才能重载，在这之前，同一浏览器里新开的标签页会一直显示连接中。
- 服务端不需要兼容旧的帧格式。

## 考虑过的方案

- **本地库继续在版本不一致时重建**：最简单，但每次发布都会清掉所有设备上的秘密聊天历史。
- **把本地库拆成可以重建的缓存库和只做增量迁移的密钥库**：以后大部分升级仍然可以直接重建，但秘密聊天消息要从 `messages` 表里拆出去，查询、搜索与列表都要合并两处来源，改动太大。
- **协议向后兼容一段时间**：旧标签页可以继续工作，但每次改协议服务端都要同时理解新旧两种帧；SW 本来就是网络优先，强制重载的代价更小。
