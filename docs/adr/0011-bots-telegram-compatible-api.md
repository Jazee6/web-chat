# ADR-0011：Bot 是特殊的 UserDO，API 兼容 Telegram Bot API 的子集

- 状态：暂缓（2026-10-09 决定暂不做；做了一半的代码已经删除，将来按这里的设计重新实现）
- 日期：2026-10-09

## 背景

第三阶段加入 Bot：由用户创建、由外部程序通过 HTTP 操控的账号，更新以 Webhook 推给程序。现有的 ID 都是字符串（用户是 better-auth 的随机 ID，私聊是 `a:b`，群组是 `g_…`），而一个相册是一条消息、一个 `seq`。免费套餐最紧的是 DO 行写入与 Worker 的 10ms CPU。

## 决策

- **API 兼容 Telegram Bot API 的子集**：路径、方法名、参数、`Update` 与错误的结构都照 Telegram，现成的库（grammY、python-telegram-bot、aiogram……）改一下 API 根地址就能用。没实现的方法返回 Telegram 格式的错误；不影响语义的可选参数忽略。
- **每个 Bot 一套自己的整数 ID**：Bot 的 `UserDO` 给它见到的每个用户与群组分配整数，第一次见到时写 1 行（用户为正、群组为负、私聊即对方用户的数）。`message_id = seq × 16 + 相册内序号`，相册按 Telegram 的方式拆成共用 `media_group_id` 的多条。同一个用户在不同 Bot 里的数不同。
- **Bot 是特殊的用户**：D1 `user` 表里一行（邮箱为保留的占位地址，按邮箱查找时排除），另有 D1 `bot` 表记录数字 ID、创建者、用户名与简介；运行时就是一个 `UserDO`，扇出、成员、拉黑等沿用用户的路径。Token 为 `<数字 ID>:<随机串>`，Worker 据数字 ID 直接找到 Bot 的 `UserDO` 校验哈希，每次调用不查 D1。
- **Webhook 在 Bot 的 `UserDO` 里排队**：更新入队 1 行、送达删 1 行，一次只有一个在途，失败按退避由 Alarm 重试，最多保留 24 小时。
- **群组的隐私模式在 `ChatDO` 扇出之前过滤**：Bot 只收到提及它、回复它的消息、命令与服务消息，从不收到其他 Bot 的消息；与 Bot 无关的群消息不扇出给它，[ADR-0002](./0002-write-fanout-small-groups.md) 的成本上界不变。

## 考虑过的方案

- **自定义的精简 API**（ID 与字段用本项目自己的）：实现更小、语义不打折扣，但每个 Bot 都要手写客户端，现成的库与教程都用不上。
- **直接把字符串 ID 交给 Bot**：零成本，JS 的库运行时大多能过，但 aiogram 等用 pydantic 强校验的库会直接失败，兼容就名不副实。
- **相册只交第一项**：`message_id = seq` 更直观，但 Bot 拿不到相册里其余的项。
- **长轮询 `getUpdates`**：本地开发方便，但挂住的请求让 DO 一直处于活动状态、计入时长。

## 后果

- `message_id` 与 `seq` 不相等，所有进出 Bot API 的消息 ID 都要换算；接入的库一旦依赖这些数，改动就要所有 Bot 跟着改。
- 兼容只能做到"常用的路径能跑"：边角行为（ReplyKeyboard、ForceReply、发送媒体、命令范围等）没做，库调用到时报错或被忽略。
- 和 Bot 有关的更新每条至少 2 行写入（入队与出队），加上整数映射每个新对象 1 行。
